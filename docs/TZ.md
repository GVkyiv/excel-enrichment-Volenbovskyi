## 1. Мета

Побудувати систему, яка приймає Excel-файл і текстовий опис завдання
природною мовою, самостійно визначає, яких даних бракує, знаходить їх у
відкритих джерелах, дописує колонки і зберігає збагачений файл. Код не
змінюється при зміні типу завдання: усе, що залежить від завдання, система
виводить сама з тексту завдання і структури файлу.

Цільова оцінка 100 балів зі 100 за рубрикою курсу (розділ 13).

## 2. Інтерфейс

```python
process_excel(
    file_path: str,
    task_description: str,
    overwrite: bool = False,
    max_workers: int = 8,
    road_mode: bool = True,
) -> EnrichmentReport
```

Результат: файл `<назва>_enriched.xlsx` поряд із вхідним плюс об'єкт звіту
(кількість рядків, заповнено, не знайдено, помилок, викликів моделі, мережевих
запитів, час, вартість).

Приклад виклику:

```python
process_excel(
    file_path="Data/Input/capitals.xlsx",
    task_description="знайди пряму відстань між столицями в км для колонки distance",
)
```

## 3. Вхідні дані

Файли лежать у `Data/Input/`, еталони викладача в `Data/Reference/`.

| Файл | Колонки | Рядків | Завдання |
|---|---|---|---|
| `capitals.xlsx` | Capital_From, Country_From, Capital_To, Country_To, distance | 10 | пряма відстань між столицями в км |
| `mountains.xlsx` | Mountain, Country, height | 10 | висота гір у метрах |

Увага: у тексті завдання курсу вказано 5 і 4 рядки, у реальних файлах по 10.
Орієнтуватись на файли.

## 4. Архітектура

Оркестрація на LangGraph. Граф описує обробку **одного рядка**, рядки
виконуються паралельно через `ThreadPoolExecutor`, у кожного рядка власний
`thread_id`. Планувальник викликається один раз на файл, до графа.

```
file_reader (код)  ->  planner (LLM, 1 виклик на файл)
                              |
                              v
        [ThreadPoolExecutor по рядках, для кожного рядка граф:]
             researcher (код + інструменти, LLM тільки в гілці відкату)
                              |
                              v
                       validator (код)
                         |          |
                   не пройшов    пройшов
                         |          |
       назад у researcher іншим     |
       інструментом, до 2 спроб     v
                                writer (код)
```

Розподіл ролей свідомий: моделі віддається тільки те, що вимагає розуміння
природної мови (розбір завдання і витягання значення з тексту сніпета). Усе,
що задається формулою або структурованим джерелом, рахує код. Це прямий
висновок ДЗ9 цього ж курсу: повністю LLM-архітектура дала ту саму точність
дорожче і повільніше.

## 5. Контракт плану (вихід планувальника)

Планувальник отримує: назви колонок, три приклади рядків, текст завдання.
Повертає строго типізований об'єкт Pydantic. Невалідна відповідь моделі це
помилка, а не привід «здогадатись».

```python
class ValidationBounds(BaseModel):
    min_value: float | None
    max_value: float | None

class EnrichmentPlan(BaseModel):
    target_column: str            # куди писати, існуюча або нова колонка
    value_type: Literal["number", "date", "text"]
    unit: str | None              # "km", "m", None
    tool: Literal["geo_distance", "wikidata_lookup", "web_search_extract", "llm_knowledge"]
    input_columns: dict[str, str] # аргумент інструмента -> назва колонки
    wikidata_property: str | None # наприклад P2044 для висоти
    search_query_template: str    # шаблон із підстановкою {Колонка}
    bounds: ValidationBounds
    ambiguous_interpretations: list[str] = []  # напр. ["straight", "road"]
    extra_columns: dict[str, str] = {}         # назва колонки -> трактування
    reasoning: str                # коротке пояснення вибору, іде в лог
```

Неоднозначність визначень: якщо планувальник бачить, що поняття в завданні
має кілька усталених трактувань (відстань пряма і дорогами), він заповнює
`ambiguous_interpretations` і `extra_columns`. Основна колонка отримує те
трактування, яке прямо назване в тексті завдання («пряма відстань» це велике
коло), додаткова колонка `distance_road_km` отримує друге. Для однозначних
величин (висота гори) режим не вмикається.

## 6. Реєстр інструментів

| Інструмент | Вхід | Вихід | Джерело | Обмеження |
|---|---|---|---|---|
| `wikidata_lookup` | список сутностей, ідентифікатор властивості | значення на сутність | Wikidata SPARQL | пакет до 50 сутностей одним запитом |
| `geo_distance` | дві назви міст, режим straight або road | км | координати P625 плюс гаверсинус, для road публічний OSRM | OSRM не розпаралелювати, до 1 запиту в секунду |
| `web_search_extract` | пошуковий запит, очікуваний тип і одиниці | значення плюс URL | Tavily (основний), ddgs (резерв) | безкоштовний тариф 1000 запитів на місяць |
| `llm_knowledge` | питання | значення | `gpt-5.6-luna` | тільки як третій рівень, див. розділ 7 |
| Nominatim | назва міста | координати | OSM | 1 запит у секунду, обов'язковий User-Agent |

Модель: `gpt-5.6-luna` напряму через OpenAI API (не через OpenRouter: в ДЗ11
зафіксовано непередбачуваний час відповіді, від 95 до 1105 секунд на одній
комбінації). Ключ береться зі змінної оточення, у коді ключів немає.

## 7. Політика достовірності

Три рівні джерел, від них залежить, чи потрібна друга перевірка.

1. **Структуроване джерело** (Wikidata, розрахунок за координатами):
   приймається одразу, друге джерело не запитується, бо не зробить значення
   точнішим.
2. **Пошуковий сніпет**: обов'язкова друга перевірка іншим джерелом або
   повторним запитом з іншим формулюванням. Причина: у тексті легко переплутати
   одиниці або взяти число з сусіднього речення.
3. **Пам'ять моделі**: приймається тільки якщо збіглась із зовнішнім джерелом.
   Інакше комірка лишається порожньою, у лог іде статус `unconfirmed`.

Правило розбіжності: якщо два джерела розійшлись більше ніж на 10%, значення
не викидається, у комірку йде значення авторитетнішого джерела, у лог
записуються обидва числа і позначка `ambiguous`.

## 8. Валідація значення

Послідовно: відповідність типу з плану, приведення одиниць (милі в км, фути в
метри), перевірка меж `bounds`, для дат перевірка діапазону 1850 до сьогодні.
Не пройшло: повернення в `researcher` іншим інструментом, максимум дві спроби,
далі статус `not_found`.

## 9. Обробка помилок

Система ніколи не падає на рядку: помилка рядка це статус рядка, а не аварія
процесу. Обов'язкові сценарії, кожен із власним зрозумілим повідомленням
українською:

| Сценарій | Поведінка |
|---|---|
| Сутності не існує (`Atlantis`) | комірка порожня, статус `not_found`, повідомлення з пошуковим запитом |
| Порожня комірка у вхідних даних | рядок пропускається, статус `skipped_empty_input` |
| Немає колонки, яку просить завдання | цільова колонка створюється; якщо бракує вхідної колонки, робота зупиняється з поясненням, якої саме колонки бракує |
| Невалідний ключ API | зрозуміле повідомлення про ключ, автоматичний відкат на резервне джерело, якщо воно є |
| Обрив мережі, таймаут | три спроби з паузами 1, 2, 4 секунди, таймаут 10 секунд на запит, далі статус `network_error` |
| Значення поза межами `bounds` | не записується, статус `out_of_bounds`, обидва числа в лог |

Для демонстрації робиться окремий файл `Data/Input/broken.xlsx`, що містить усі
ці випадки, і секція в ноутбуці, де видно, що система доходить до кінця і
зберігає файл.

## 10. Формат вихідного файлу

Запис через `openpyxl` поверх копії оригіналу. `pandas.to_excel` заборонений:
він перезаписує книгу і втрачає форматування, а вимога курсу це збереження
оригінальних даних без змін.

- Аркуш 1: структура оригіналу плюс заповнена цільова колонка плюс додаткові
  колонки, якщо план їх передбачив. Заповнюються **тільки порожні комірки**,
  наявні значення не чіпаються ніколи (`overwrite=False` за замовчуванням).
- Аркуш 2 `enrichment_log`, по рядку на кожен оброблений рядок:

  `row_index | target_column | value | unit | tool | source_url | query | confidence_level | status | message | duration_ms | llm_calls`

- Друк у консоль підсумку: скільки заповнено, скільки не знайдено, скільки
  помилок, скільки пропущено вже заповнених, скільки викликів моделі і мережі,
  час, оцінена вартість.

Формат значень: числа як числа (не текст), дати текстом `ДД.ММ.РРРР`, порожньо
при невдачі (жодних заглушок на кшталт «немає даних» у числовій колонці).

## 11. Ефективність

- Wikidata запитується пакетами, а не порядково: 1000 рядків це одиниці
  запитів, а не тисячі.
- Кеш `cache.sqlite`, ключ це пара «інструмент плюс нормалізований запит».
  Повторний прогін не витрачає ні мережу, ні гроші.
- Паралелізм `ThreadPoolExecutor`, за замовчуванням 8 потоків, налаштовується.
  Джерела з лімітом (Nominatim, OSRM) викликаються послідовно з дотриманням
  1 запиту в секунду.
- Виклики моделі: один на файл в основному шляху. Виклик на рядок тільки в
  гілці відкату, коли детерміноване джерело не спрацювало.
- Стрес-тест на 1000 згенерованих рядків, у README два заміри: холодний кеш
  (реальна мережа) і теплий. Дорожній режим на стрес-тесті вимикається
  прапорцем через ліміти публічного OSRM, це записується як свідоме обмеження.

## 12. Демонстрація універсальності

Той самий код, без жодної зміни, на чотирьох завданнях:

1. `capitals.xlsx`, пряма відстань у км (детермінований шлях, розрахунок).
2. `mountains.xlsx`, висота в метрах (детермінований шлях, Wikidata).
3. `capitals.xlsx`, населення міста (видно, як планувальник обирає Wikidata, і
   як працює відкат у пошук).
4. `mountains.xlsx`, повна дата першого успішного сходження, формат
   `ДД.ММ.РРРР`, тип `date`, межі 1850 до сьогодні (тип не числовий, тобто
   допуск ±10% до нього не застосовний, це доводить роботу з різними типами).

## 16. Свідомі обмеження

- Berlin-Vienna 779 км в еталоні не пояснюється жодним джерелом. У README
  фіксуються три числа (пряма 524, дорога близько 680, еталон 779) і чесне
  «походження невідоме», з версією про залізничний маршрут як припущенням.
- Дорожній режим на стрес-тесті вимкнений через ліміти публічного OSRM.
- Максимально досяжна збіжність з еталоном викладача при чесному розрахунку
  становить 85% по двох наборах, і це властивість еталону, а не системи.
